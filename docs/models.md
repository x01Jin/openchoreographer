# Models

A subagent's primary model resolves in this order: the dialog override first, else `agents.<id>.model` from the host config, else the model the agent inherits from the parent session. Dialog overrides live in the plugin's own settings storage, not in `opencode.jsonc` or the agent `.md` files. The plugin never changes a configured agent model itself.

Fallbacks are set the same way, in the `/choreographer` dialog only: per agent, or for a whole group with the `all workers` and `all reviewers` rows. There is no config option for them. A `fallback` key left in the plugin's `options` block is ignored, and setup logs one warning about it.

A model ref is `provider/model`, optionally followed by `#variant` (for example `opencode-go/deepseek-v4.1-flash`). An agent with no fallback override in the dialog has no fallbacks, and the orchestrator is excluded from fallback handling entirely.

A failure whose message names a quota, usage limit, or billing problem, or which carries status 402, marks that model down at once with reason `quota`, and there is no retry on that model. A failure with status 408, 429, or 5xx, a timeout or network error, or anything unrecognized is retryable. Any other 400-range status, or an invalid or unsupported request, is fatal and is surfaced with no retry and no fallback. Availability is tracked per `provider/model`, so variants share one entry and one exhausted model affects every agent that uses it. A down mark lasts a fixed 5 minutes, with no doubling; after it expires the primary is used again.

A down mark clears in exactly two ways: five minutes passing since the last failure on that model, or the manual restore from the sidebar. A worker finishing successfully does not clear it; success clears only the degraded flag. Each new failure restarts the five minutes, so a model that keeps failing stays marked. The mark is per `provider/model`, so restoring it from one row clears it for every agent that uses that model; restoring only makes the plugin willing to try the primary again, so a still-exhausted model is marked down again on its next failure. A child's model is picked when it is spawned; a running child keeps it and is never moved mid-run, and a resumed session is not reassigned either.

Before a subagent is spawned the plugin picks the first model that is not marked down and passes it to the call. A model supplied explicitly by the caller is left alone unless it is already marked down. When no alternate is available the plugin still tries the last one rather than failing. A retryable failure is retried in the same child session, one more time (two attempts total; `attempt` 1 is the initial request). The delay is the provider hint when one is present, else 1s, capped at 15s. A retry that succeeds leaves the model in use but flags it degraded: the next first-attempt failure on that model goes straight to the fallback. The second failure marks the model down with reason `retries` and the spawn is run once more on the fallback model. A failure on a model that is not down, for an agent with no fallback, propagates untouched.

That re-run only covers a call that waits for the child. A background call returns its sessionID before the child runs, so a failure inside the child surfaces in the child session, not as a thrown spawn error, and the parent sees the sessionID; the failed background child is not re-run on the fallback. Failures in any session still go through the same retry hook, so once the model is marked down, later spawns route to the fallback. An agent with no configured fallback keeps the host's retry behavior: the plugin neither forces nor vetoes retries for it.

The read-only `fallback_status` tool reports each managed agent's primary model, its dialog fallbacks, and whether any model is down or degraded, so you can tell which model a worker will use before spawning it. See [tools](tools.md) for its output shape.

An agent with no configured model inherits the parent session model. When that inherited default is a free-tier model, quota failures hit every spawn, and without a fallback there is nothing to switch to. Set a fallback before relying on that setup.
